# dapen-golang-next — Hermes Config

Project-specific Hermes Agent configuration. Auto-loaded by Hermes when CWD is inside this project.

## Project Identity

- **Name:** dapen-golang-next
- **Type:** Go backend (Gin) + React 19 frontend (TanStack Start)
- **Architecture:** Domain-Based + DDD-Lite + Layered (backend), strict separation (frontend)
- **Database:** SQL Server 2008 R2 (legacy, Laravel origin), MongoDB, Redis
- **Kanban board:** `dapen-golang-next` (use `hermes kanban boards switch dapen-golang-next`)

## Agent Routing (Project-Specific)

For this project, the orchestrator MUST dispatch tasks to one of the **3 dapen agents only**:

| Agent | Scope | Files |
|---|---|---|
| `dapen-backend` | Backend Go (Gin, GORM) | `backend/**/*.go`, `cmd/`, `internal/` |
| `dapen-frontend` | Frontend React 19 (TanStack Start) | `frontend/src/**/*.{ts,tsx}`, `frontend/src/server/` |
| `dapen-qa` | E2E (Playwright) + unit tests | `**/*_test.go`, `**/*.test.ts`, `tests/e2e/` |

**Do NOT dispatch to** `golang-standard`, `tanstack-start-standard`, `database-architect`, or `laravel-standard` for this project — even though those profiles exist. The 3 dapen agents are the project-specific experts.

## Multi-Layer Detection

If a task touches BOTH `backend/**` AND `frontend/**`, dispatch in parallel:
- `dapen-backend` for backend files
- `dapen-frontend` for frontend files
- Optionally `dapen-qa` for the test layer

Use `hermes kanban link` to express dependencies (e.g. frontend depends on backend API being defined first).

## Quality Gate (User-Runs-Only)

The user runs `./scripts/check-all.sh` (or `--backend-only` / `--frontend-only`). Workers do NOT execute check-all, `go test`, `npm test`, `npx playwright test`, `swag init`, `npm run dev`, or `git` write operations. They create the artifacts; the user runs the gate.

This is per-project CLAUDE.md Rule #16 + global `user-driven-quality-gates` skill.
